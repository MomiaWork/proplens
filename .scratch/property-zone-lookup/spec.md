# Phase 1: 物件查詢服務（實價登錄 ETL + 都市計畫 GIS 疊圖）

## Problem Statement

PropLens 要把分散在多個政府開放資料源的客觀資訊，整合成單一結構化的「物件資訊卡」，供使用者自行判斷或貼給外部 AI 工具分析——App 本身不做任何主觀投資判斷或估價（避免觸碰《不動產估價師法》紅線）。

在投入完整開發之前，需要先驗證一個未知的技術風險：實價登錄交易資料能否可靠地下載入庫，並與台中市都市計畫圖資做地理疊圖（point-in-polygon），產生出對「物件」有意義的周邊客觀資訊。這是整個專案唯一未經驗證的技術環節，其餘資料源（捷運、學區、人口、嫌惡設施）風險較低，排在後續 Phase。

## Solution

建立一個單一進入點的「物件查詢」服務：輸入一個台中市地址字串，回傳該地址所在的都市計畫分區，以及同分區內近期的有效交易統計（或樣本不足時的原始清單），或明確的失敗訊息。

服務內部串接兩條資料管線：

1. **實價登錄 ETL**：定期下載、解析、過濾、入庫有效交易紀錄
2. **都市計畫圖資疊圖**：以本地儲存的都市計畫圖資檔案，對物件座標做 point-in-polygon 判定

兩者在查詢時於「物件查詢」服務內合併，對外只有一個介面，不需要呼叫方了解內部的 ETL / 疊圖細節。

## User Stories

1. As a PropLens 使用者, I want to輸入一個台中市地址, so that 我能看到這個物件所在的都市計畫分區
2. As a PropLens 使用者, I want to 看到同分區近期有效交易的均價與樣本數, so that 我有客觀的價格背景資訊可以參考
3. As a PropLens 使用者, I want 當同分區有效交易筆數過少時，看到原始交易清單而不是誤導性的均價, so that 我不會被少樣本的統計數字誤導
4. As a PropLens 使用者, I want 清楚知道目前有多少筆有效交易被納入統計, so that 我能自行判斷這個均價的可信度
5. As a PropLens 使用者, I want 當我輸入的地址無法被辨識時，得到「地址無法辨識」的明確訊息, so that 我知道是我打錯字而不是系統故障
6. As a PropLens 使用者, I want 當我輸入的地址不在台中市範圍內時，得到「僅支援台中市」的明確訊息（不同於地址無法辨識）, so that 我知道問題是使用範圍而不是我打錯字
7. As a PropLens 使用者, I want 物件資訊卡上只呈現原始事實數字（分區名稱、交易金額、樣本數）, so that 我拿到的是客觀資料而不是被加工過的判斷
8. As a system, I want 只快取地址→座標的 geocoding 結果, so that 重複查詢同一地址不需要重打有額度限制的 Geocoding API
9. As a system, I want 座標→都市計畫分區的判定每次都即時比對本地最新一份圖資檔案, so that 都市計畫「不定期更新」後，分區判定不會因為快取而靜默過時
10. As a system, I want 實價登錄 ETL 只匯入 2021/7（實價登錄2.0上路）之後的交易紀錄, so that 疊圖用的地址都是完整門牌，point-in-polygon 判定結果可信賴
11. As a system, I want 實價登錄 ETL 能定期（每月1/11/21日附近）重新下載並入庫最新申報資料, so that 有效交易紀錄反映最新的申報狀態
12. As a maintainer, I want 都市計畫圖資檔案能獨立於查詢邏輯手動或排程重新下載, so that 圖資的「不定期更新」不需要額外設計快取失效機制
13. As a PropLens 使用者, I want 物件座標落在都市計畫分區交界附近時，仍然得到正確的分區判定, so that 我不會因為地址剛好在邊界而拿到錯誤的比較基準

## Implementation Decisions

- **服務邊界（唯一 seam）**：一個「物件查詢」服務，輸入地址字串，輸出以下三者之一：物件資訊卡（都市計畫分區 + 同分區有效交易統計或原始清單）、地址無法辨識、超出台中市範圍。呼叫方不需要知道內部 ETL / 疊圖細節。
- **物件（Property）**：使用者輸入的目標地址，是物件資訊卡的查詢錨點；物件本身不必然出現在實價登錄中。[[CONTEXT.md]]
- **有效交易紀錄**：僅 2021/7（實價登錄2.0）之後申報的交易紀錄才視為有效——這是唯一保證門牌完整揭露、可精準 geocoding 的資料範圍。2021/7 之前的區段化地址資料不匯入。詳見 `docs/adr/0001-exclude-pre-2021-transactions.md`。
- **同分區有效交易**：比較基準是物件座標所落入的都市計畫分區（point-in-polygon 判定），不使用半徑範圍或路段/里比對。詳見 `docs/adr/0003-same-zone-as-comparison-scope.md`。
- **最低樣本門檻**：同分區有效交易筆數低於門檻（預設 5 筆，可依實測資料分布調整）時，不計算均價，改為回傳原始交易紀錄清單並標示樣本不足。詳見 `docs/adr/0004-insufficient-sample-shows-raw-not-degraded-scope.md`。
- **客觀事實邊界**：物件資訊卡不呈現任何由服務自行計算出的比較值、差額、百分比或排名——這類運算即使是純數學，也會被解讀為隱性價值判斷，是本專案最主要的法遵風險邊界。詳見 `docs/adr/0005-no-computed-comparison-values.md`。此原則約束的是「跨物件/跨統計量的比較運算」，不影響本 spec 內「同分區均價 + 樣本數」這種單一分區內的聚合統計。
- **輸入驗證的兩種失敗情境**：地址無法辨識（Geocoding API 查無結果）與地址有效但超出台中市範圍（point-in-polygon 在所有分區都找不到落點）要回傳不同訊息，不可合併成單一「查詢失敗」。
- **快取策略**：只快取「地址 → 座標」（geocoding 結果，永久事實，用於節省 API 額度）；不快取「座標 → 都市計畫分區」的判定結果（每次即時對照本地最新圖資檔案，因都市計畫「不定期更新」，快取會有靜默過時風險）。詳見 `docs/adr/0007-cache-geocoding-only-not-zone-lookup.md`。
- **都市計畫圖資取得方式**：經查證，台中市都市計畫圖(GIS)資料集提供 API 介接（Swagger），更新頻率為「不定期更新」，每筆分區資料帶有「修圖日期」欄位。這與原始摘要中「無官方REST API」的認知（該認知描述的是實價登錄資料，不是都市計畫圖資）不同，圖資下載機制應採 API 介接而非純檔案下載。
- **Geocoding 供應商**：POC 階段使用 Google Maps Geocoding API（免費額度每日 2500 次），地址查詢限定台中市範圍避免同名路段誤判。

## Testing Decisions

- 針對「物件查詢」服務這個單一 seam 做黑箱測試，不對內部 ETL / point-in-polygon / 聚合邏輯個別開測試點——這是本 spec 談定的唯一 seam。
- 測試案例覆蓋以下四種情境（每種至少挑 1-2 個台中市真實地址）：
  1. 一般案例——地址落在交易量正常的分區，驗證回傳正確分區名稱 + 均價 + 樣本數
  2. 分區交界案例——地址在兩個都市計畫分區邊界附近，驗證 point-in-polygon 不會抓錯分區
  3. 樣本不足案例——地址落在冷門分區（如農業區/剛重劃區），驗證回傳原始清單 + 樣本不足標示，而不是失真的均價
  4. Geocoding 失敗與超出範圍案例——分別測試地址打錯字（查無結果）與有效但非台中市地址（point-in-polygon 找不到分區），驗證回傳訊息不同
- 只在服務邊界（geocoding API 呼叫）做 stub/fake，不 mock 服務內部的 ETL 或疊圖邏輯——這兩者是本 spec 要驗證的核心技術風險，用真實邏輯測試才有意義。
- 這是本專案第一次寫測試，暫無既有測試慣例可參考；優先以黑箱、行為導向的方式建立第一批測試，作為後續 Phase 的參考範本。

## Out of Scope

- Phase 2 資料類別（捷運距離、人口/戶數趨勢、學區、嫌惡設施）——留待 Phase 1 資料結構穩定後再擴充
- UI／物件資訊卡的視覺呈現——待 Phase 1 + 2 資料結構穩定後才做（避免資料結構變動導致重工）
- Prompt Builder（「產生 AI 分析 Prompt」一鍵匯出功能）——屬於呈現層/Phase 3，本 spec 只處理資料層
- 使用者輸入物件開價、與同分區均價比較——本 spec 未涉及使用者輸入開價這個欄位；`docs/adr/0005-no-computed-comparison-values.md` 訂下的原則（不計算比較值）是為未來實作這類功能時的約束，非本 spec 的實作項目
- 2021/7 之前的歷史實價登錄資料（區段化地址）——明確排除，見 `docs/adr/0001`
- TGOS / Map8 等替代 Geocoding 供應商評估——POC 階段先用 Google Maps Geocoding API，正式階段再評估
