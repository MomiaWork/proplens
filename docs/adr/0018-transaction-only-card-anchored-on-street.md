# ADR-0018: 目前的物件資訊卡只用實價登錄，並以「同路段」為範圍

## Status

Accepted — 暫時性，取代 ADR-0003 的範圍定義直到分區圖資到位

## Context

ADR-0003 把「同分區有效交易」定為物件資訊卡唯一的比較基準，CONTEXT.md 並明
文寫著「不使用半徑範圍或路段/里比對」。那個設計成立的前提是每個支援的縣市
都有都市計畫分區圖資。

ADR-0017 加入新竹市之後，這個前提破了。新竹市四份資料裡有兩份（GIS門牌、學
區表）沒有任何可自動或人工穩定取得的來源，都市計畫分區圖資也只查到互動式圖
台、沒查到可下載的 shapefile（見 `.scratch/city-selection/research.md`）。唯一
兩市對等、且已實際驗證可產出的，是實價登錄。

分區是整張卡的錨點：`AddressToZoneService` 解不出分區，查詢就直接結束，均價、
樣本數、學區全部不會跑。所以「新竹市只有實價登錄」的實際效果不是資訊少一
點，而是**完全查不到東西**。

## Decision

**app 目前組出來的卡片只讀 `<city>-transactions.sqlite`，範圍是同路段。**

- **同路段 = 同街名（+ 同行政區，當地址寫得出行政區時）。** 街名由
  `parseAddress` 從查詢地址取出，交易那側則在 ingest 時就用同一個函式算好存進
  `street`/`district_code` 欄位——同一份程式碼算兩邊，手機端查詢就只是一次索引
  查表。台中市的 中山路 同時存在於多個行政區，所以行政區有寫時要一起比對；沒
  寫時回傳該街名全市的交易，而不是挑一個行政區。
- **卡片列出原始交易紀錄，不出任何聚合數字。** 每筆帶：房屋類別（建物型態）、
  交易類別（交易標的）、主要用途、建成年份（建築完成年月）、坪數、每坪單價、
  總價、使用分區。全部是實價登錄公告的欄位，或它的單位換算（平方公尺 → 坪，
  1 坪 = 3.305785 m²）——換算不是 ADR-0005 所禁止的「把多個事實組合成單一評價
  信號」。
- **刻意不給均價。** 同路段比同分區鬆得多，一個標題數字會帶有這個範圍撐不起
  的權威感。筆數有給，原始紀錄有給，判斷留給使用者（ADR-0002、ADR-0005）。
- **來源沒揭露的欄位留空顯示「不詳」，不填 0。** 預售屋沒有建築完成年月，非都
  市土地沒有使用分區，這些是真的沒有，不是零。
- **同步只下載實價登錄那一份。** `DATA_FILE_KEYS` 只剩 `transactions`，於是首次
  同步從 ~200MB 降到 ~150KB，而且不再需要開機後跑一輪 on-device geocoding
  enrichment（ADR-0014）就能查詢。

**分區與學區的引擎沒有刪除。** `propertyQueryService.ts`、`zoneLookup.ts`、
`schoolDistrictLookup.ts`、`enrichTransactionZones.ts` 與它們的測試全部留著且
持續通過；pipeline 也還會建那四份檔案。改變的只是 app 組合了哪一條路徑。

## Consequences

- **兩個縣市今天就真的可以查。** 已用真實資料驗證：台中市 688 筆、新竹市 129
  筆，街名拆解失敗 0 筆，坪數 817/817 筆有值，建成年月 815/817 筆有值。
- 查詢地址本身不需要在實價登錄裡出現——它仍然只是錨點（ADR-0002 不變）。
- 拆不出門牌的交易（`柑林段353地號` 這種土地交易）街名留空，同路段查詢撈不
  到；它們仍留在檔案裡。
- **這條與 ADR-0003 直接衝突，且是刻意的。** 分區圖資對所有支援縣市到位後，
  應該回到同分區，並把同路段降為輔助或移除——屆時請更新這份 ADR 而不是默默改
  程式。
- ADR-0016（測試跑的是實際出貨的引擎）在字面上有一塊鬆掉了：分區/學區引擎仍
  被測試，但目前沒有被 app 組合進去。保留它們是因為它們是可運作、已驗證的程
  式碼，而缺的是資料不是程式碼；刪掉再寫一次的成本遠高於留著。
